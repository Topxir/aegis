## 1. Что такое Aegis (коротко)

Анонимный мессенджер с максимальным приоритетом безопасности.
- Регистрация: **ник + пароль**. Никаких номеров, почт, привязки к личности.
- Все данные хранятся **на устройстве**, зашифрованы. Взлом сервера не раскрывает переписку.
- Повседневный вход: **PIN** (быстро). После переустановки: ник + пароль.
- Федерация: любой поднимает свой сервер **из самого клиента**. Есть список серверов с подписанными галочками ✓ (официальные/проверенные).
- Пользователей нельзя найти поиском. Добавление только по приглашению (ссылка/QR).
- Сообщения, звонки и видеозвонки приходят в фоне, с низкой задержкой.
- Плагины и моды. Всё открыто на GitHub, всё анонимно.
- Масштаб на старте: мало пользователей. Проектируй для малого, но не блокируй рост.

**Безопасность важнее удобства, удобство важнее красоты, красота важнее скорости разработки.**

## 2. Нерушимые правила (нарушение = задача не принята)

1. **Никакой самописной криптографии.** Только проверенные библиотеки и протоколы (см. PLAN.md §5). Нужен новый примитив — запись в `DECISIONS.md` и одобрение владельца.
2. **Никакой телеметрии, аналитики, краш-репортов наружу, сторонних SDK, Firebase/Google Play Services в ядре.**
3. **Никаких номеров, почт, IP-логов, глобальных идентификаторов пользователя.** Сервер хранит минимум, см. PLAN.md §6.
4. **Секреты никогда не попадают** в логи, исключения, скриншоты, бэкапы в открытом виде, буфер обмена, превью задач/уведомлений.
5. **Fail closed:** при любой ошибке проверки подписи/MAC/сертификата — отказ, а не «пропустим».
6. **Слои не смешиваются:** UI не знает про криптографию, крипто-ядро не знает про UI, плагины не видят ключей.
7. **Память:** ключи в `zeroize`-буферах, без копий в строки, без логирования.
8. **Новая зависимость** = запись в `DECISIONS.md` (зачем, лицензия, аудит, альтернативы), версия и хэш закреплены. Меньше зависимостей — лучше.
9. **Не ослабляй безопасность ради удобства** без явного одобрения владельца. Если сомневаешься — спроси.
10. **Не выдумывай.** Не знаешь — пиши в `QUESTIONS.md` и спрашивай. Не заявляй «готово» без проверки.

## 3. Карта модулей (ядра)

| Модуль | Ответственность | Зависит от |
|---|---|---|
| `aegis-crypto` | Обёртки над проверенными либами: KDF, AEAD, подписи, KEM, ratchet | — |
| `aegis-identity` | Ник/пароль, OPAQUE-логин, ключи аккаунта, PIN-слой, переустановка | crypto |
| `aegis-storage` | Локальная зашифрованная БД, миграции, wipe | crypto |
| `aegis-protocol` | Сообщения, чаты, группы, ratchet-сессии, вложения, формат пакетов | crypto, identity, storage |
| `aegis-transport` | Соединения клиент↔сервер, фон, реконнект, прокси/Tor, паддинг | protocol |
| `aegis-calls` | Голос/видео, E2EE медиа, TURN/ICE, адаптивный битрейт | protocol, transport |
| `aegis-server` | Сервер федерации: очереди, TURN, сертификаты, нулевое знание | protocol |
| `aegis-directory` | Подписанный список серверов, галочки ✓, отзыв, проверка подписей | crypto |
| `aegis-launcher` | Мастер запуска своего сервера из клиента (VPS/десктоп/Docker/onion) | server, directory |
| `aegis-plugins` | WASM-песочница, манифесты прав, реестр, темы | protocol (ограниченно) |
| `aegis-ui-*` | Интерфейсы по платформам (Android, desktop, позже iOS) | всё через публичное API ядра |

Правило: меняя модуль, не трогай чужие. Нужна правка соседнего модуля — отдельная задача или запись в `QUESTIONS.md`.

## 4. Контракты интерфейсов

- Каждый модуль имеет `docs/contracts/<модуль>.md`: публичное API, типы, ошибки, гарантии, что **запрещено** вызывающему.
- Публичное API меняется **только** через задачу с пометкой `contract-change` + обновление контракта + миграция + запись в `DECISIONS.md`.
- Протокол и формат данных версионируются (`protocol_version`, `schema_version`). Обратная совместимость или явная миграция обязательны.
- Любое API ядра для UI — через единый слой (FFI/UniFFI). UI не лезет внутрь.

## 5. Рабочий цикл задачи

1. **Вход** (§0).
2. **План:** выпиши шаги, затрагиваемые модули, риски, как будешь проверять. Для безопасностно-значимых изменений — сначала мини-модель угроз (3–5 строк).
3. **Тесты вперёд:** сначала тест/критерий приёмки, потом код.
4. **Реализация** в рамках задачи. Без «заодно перепишу».
5. **Проверка:** юнит, интеграционные, линтеры, `cargo audit`/аналог, фаззинг парсеров (если трогал парсинг).
6. **Саморевью по чек-листу** (§6).
7. **Отчёт** (§7) и обновление `STATE.md`.
8. **Остановись.** Не бери следующую задачу сам.

## 6. Политика «без багов»

Определение «готово» (Definition of Done) — все пункты обязательны:
- [ ] Критерии приёмки из задачи выполнены и проверены тестами
- [ ] Покрыты граничные случаи: пустые данные, огромные данные, обрыв сети, повтор, переупорядочивание, повреждённый ввод
- [ ] Нет `unwrap`/паник на внешних данных; все ошибки типизированы
- [ ] Парсеры внешних данных прошли фаззинг (или заведена задача на это)
- [ ] Нет секретов в логах (проверено поиском)
- [ ] CI зелёный: сборка, тесты, линтеры, аудит зависимостей
- [ ] Контракт и документация обновлены
- [ ] Отчёт написан, `STATE.md` обновлён
- [ ] Известные баги записаны в `docs/BUGS.md` (ничего не скрыто)

Нашёл баг (даже чужой, даже вне задачи) — **не молчи**: запиши в `BUGS.md` (ID, шаги, серьёзность, модуль). Уязвимость — серьёзность `SEC`, сообщи владельцу сразу.

## Вопросы владельцу
- ссылки на QUESTIONS.md

Дополнительно обновляй:
- `docs/STATE.md` — текущее состояние по модулям (✅ / 🔧 / ❌ + дата).

- `docs/BUGS.md` — баги и уязвимости.
- `docs/QUESTIONS.md` — вопросы владельцу и статус ответа.

## 8. Когда спрашивать (обязательно)

Спрашивай владельца, если:
- задача или требование неясны, противоречат друг другу или `PLAN.md`;
- нужно решение, влияющее на безопасность, анонимность, протокол или формат данных;
- нужна новая зависимость или внешний сервис;
- нужно ослабить любое правило из §2;
- не уверен, что проверка достаточна.

Формат вопроса: суть → варианты → твоя рекомендация и почему → что блокируется. Один вопрос — одно решение. Не угадывай молча.

## 10. Стиль работы

- Коротко и по делу, без воды. Факты, не обещания.
- Если что-то не проверено — так и пиши («не проверено»).
- Код читаемый, комментарии объясняют «почему», а не «что».
- Публичное API и протокол документируй в момент создания.
- Коммиты маленькие и атомарные, сообщения: `T-XXXX: что и зачем`.
- Коммиты и репозиторий анонимны: никаких личных email/имён в метаданных, использовать проектную идентичность.

**Если сомневаешься — остановись и спроси.**
