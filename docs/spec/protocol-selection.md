## 1. Сравнение сетевых моделей: Аккаунты vs Односторонние очереди vs Гибрид Aegis

Ключевая задача архитектуры Aegis — совместить **привычный вход по нику и паролю при переустановке приложения** (без номеров телефонов и обязательного выписывания 24 слов на бумажку) с **невозможностью поиска пользователей и нулевым знанием сервера о социальном графе**.

### 1.1 Сравнительная таблица вариантов

| Критерий | Вариант A: Классические аккаунты на сервере (Matrix / XMPP / классический мессенджер) | Вариант B: Чистые односторонние очереди без аккаунтов (SimpleX-подобная модель) | Вариант C (Выбор Aegis, D-0002): Гибрид `OPAQUE AccountVault` + Односторонние анонимные очереди + `Sealed Sender` |
|---|---|---|---|
| **Идентификация на сервере** | Глобальный `user_id` (`@nick:server`) виден серверу при каждом чтении/отправке | Нет аккаунтов; только анонимные очереди (`QueueId`) | Двухслойная: для входа/синхронизации — обезличенный `login_id = BLAKE3(server_salt, Argon2id(nick))` по протоколу **OPAQUE**; для переписки — только не связанные с `login_id` односторонние очереди |
| **Защита метаданных и графа контактов** | Низкая: сервер видит, какой `user_id` кому пишет или чью очередь читает | Максимальная: у каждого контакта своя пара очередей без общего `user_id` | **Максимальная:** сервер видит только запись и чтение несвязанных `QueueId` с фиксированным паддингом (`256B`..`16KB`); список очередей пользователя зашифрован внутри `AccountVault` ключом из пароля |
| **Невидимость пользователей (отсутствие поиска)** | Требует искусственных запретов на сервере; злой сервер всё равно знает список ников | Полная: пользователей физически не существует как адресуемых сущностей | **Полная:** сервер не знает ников (`login_id` необратим), а отправка сообщений возможна только при наличии криптографического токена записи (`write_cap_token`) из одноразового инвайта |
| **UX переустановки и входа с нового устройства** | Удобно: ввод логина и пароля | Плохо: при потере телефона без ручного файлового экспорта БД все очереди и контакты теряются навсегда | **Отлично:** пользователь вводит ник и пароль -> проходит OPAQUE -> скачивает и расшифровывает свой `AccountVault` -> мгновенно восстанавливает свои односторонние очереди и контакты |
| **Устойчивость к спаму и DDoS на контакт** | Спамер, зная `@nick:server`, может бесконечно слать запросы; блокировка только в UI | Удаление конкретной входной очереди полностью отрезает спамера | **Максимальная:** 1 контакт = 1 изолированная очередь + адаптивный `BLAKE3 PoW`. Удаление очереди в 1 клик физически уничтожает адрес доставки для спамера |
| **Федерация между серверами (PLAN.md §6.4)** | S2S-федерация: сервер отправителя знает сервер и ID получателя | Прямая запись клиента в очередь на сервере получателя (C2S Direct) | **C2S Direct Write (Вариант A из PLAN.md §6.4):** клиент отправителя пишет зашифрованный пакет напрямую в анонимную очередь на сервере получателя (через Tor/VPN/TLS), не раскрывая свой домашний сервер |

### 1.2 Архитектура выбранной гибридной модели (D-0002)

1. **Слой 1: Аутентификация и `AccountVault` (OPAQUE, RFC 9807):**
   - Никнейм пользователя никогда не отправляется на сервер в открытом виде. Клиент запрашивает публичную соль сервера `server_salt` и вычисляет `login_id = BLAKE3_derive_key("aegis.login_id.v1", Argon2id(nickname, server_salt))`.
   - Регистрация и вход выполняются по протоколу **OPAQUE (RFC 9807 на Ristretto255)**. Сервер хранит только `opaque_record` и зашифрованный конверт `AccountVault`, зашифрованный алгоритмом `XChaCha20-Poly1305` на ключе, выведенном из секретного `export_key` OPAQUE.
   - Внутри `AccountVault` лежат: приватные ключи чтения активных односторонних очередей пользователя, метаданные контактов и настройки профиля. Сервер не может ни расшифровать `AccountVault`, ни связать его с очередями в своей базе.
2. **Слой 2: Односторонние анонимные очереди (`Unidirectional Queues`) и `Sealed Sender`:**
   - Для каждого контакта `B` пользователь `A` создаёт на своём сервере отдельную входящую очередь `Q_{B->A}` со случайным 256-битным `queue_id`, ключом авторизации чтения `read_auth_pubkey` (Ed25519) и токеном права записи `write_cap_token`.
   - При чтении и создании очереди `Q_{B->A}` клиент **не использует сессию OPAQUE** — запросы подписываются только одноразовым ключом очереди `read_auth_key`.
   - При отправке сообщения в очередь получателя `Q_{A->B}` клиент подключается напрямую к серверу получателя (C2S Direct), предъявляет `write_cap_token` и кладёт пакет, выровненный паддингом до ближайшей корзины: **`256 B`, `1024 B`, `4096 B` или `16384 B`**.
   - Идентификатор и подпись отправителя находятся исключительно внутри E2EE-шифротекста (**Sealed Sender**).

## 2. Сравнение криптографических реализаций (Rust)

В соответствии с `AGENTS.md §2` (никакой самописной криптографии, строгая лицензионная чистота `AGPL-3.0-or-later`, минимум зависимостей, `zeroize`) проведено сравнение трёх подходов к построению криптографического ядра `aegis-crypto` и `aegis-protocol`.

| Критерий | Вариант 1: Монолитный `libsignal-client` (форк Signal) | Вариант 2: `vodozemac` (Matrix Olm/Megolm) + `OpenMLS` | Вариант 3 (Выбор Aegis, D-0012): Модульная композиция аудированных Rust-крейтов (`RustCrypto` / `dalek` / `opaque-ke` / `ml-kem`) + `OpenMLS` (Фаза 6) |
|---|---|---|---|
| **Чистота и переносимость Rust** | Содержит тяжёлую привязку к внутренней инфраструктуре Signal (UUID аккаунтов, телефонные номера, собственные protobuf-схемы и серверные концепции Signal) | `vodozemac` чистый Rust, но жестко привязан к спецификации Matrix и не включает встроенный пост-квантовый гибрид `ML-KEM-768` в базовом рукопожатии | **100% чистый, идиоматичный Rust (`no_std`-совместимые примитивы)** без чужих серверных абстракций, идеально ложится под односторонние очереди Aegis и UniFFI |
| **Лицензионная совместимость с AGPL-3.0** | `AGPL-3.0-only` (требует осторожности при связывании с `AGPL-3.0-or-later`) | `Apache-2.0` / `MIT` (полностью совместимо с `AGPL-3.0-or-later`) | **`Apache-2.0` / `MIT` / `BSD-3-Clause`** у всех базовых крейтов -> полная совместимость с `AGPL-3.0-or-later` проекта Aegis |
| **Статус независимого аудита** | Аудирован, но форк для удаления телефонных ID потребует переписывания критического кода | `vodozemac` аудирован Least Authority; `OpenMLS` проходит регулярные проверки | Все базовые примитивы (`curve25519-dalek`, `ed25519-dalek`, `chacha20poly1305`, `sha2`, `blake3`, `argon2`, `opaque-ke`) имеют публичные независимые крипто-аудиты (NCC Group, Quarkslab, Least Authority) |
| **Поддержка PQXDH (`X25519` + `ML-KEM-768` FIPS 203)** | Есть (SPQR/PQXDH), но привязана к Signal Server PreKey Bundles | Отсутствует из коробки в `vodozemac` | **Нативная реализация стандартного гибридного KEM-комбайнера** поверх аудированного `x25519-dalek` и стандартизованного NIST FIPS 203 `ml-kem` |
| **Групповой протокол (Фаза 6)** | Sender Keys (нет Post-Compromise Security при удалении участника без пересоздания ключей у всех) | **MLS (RFC 9420, `OpenMLS`)** — современный стандарт IETF с деревами ключей TreeKEM | **MLS (RFC 9420, `OpenMLS`)** для групп в Фазе 6 + классический `Double Ratchet` с гибридным `PQXDH` для 1:1 чатов с Фазы 1 |

### 2.1 Утверждённый стек примитивов `aegis-crypto` (D-0012)

| Назначение | Алгоритм / Стандарт | Выбранный Rust-крейт | Примечания по безопасности |
|---|---|---|---|
| **Хэширование пазлов PoW и быстрый KDF** | `BLAKE3` (256 бит) | `blake3` | Режимы `hash`, `keyed_hash`, `derive_key` |
| **Стандартный KDF рэтчета и гибридного KEM** | `HKDF-SHA256` (RFC 5869) | `hkdf` + `sha2` | Строгая доменная сепарация (`info`-строки с версией протокола) |
| **KDF пароля и защита от брутфорса** | `Argon2id` (RFC 9106) | `argon2` | Параметры по умолчанию: `m = 65536 KiB (64 MiB)`, `t = 3`, `p = 4`, выход 32 байта |
| **Аутентификация по паролю (Zero-Knowledge)** | `OPAQUE` (RFC 9807, Ristretto255 + SHA-512) | `opaque-ke` | Сервер никогда не видит пароль и `export_key` |
| **Классический DH** | `X25519` (RFC 7748) | `x25519-dalek` | Проверка на малый порядок точек, `ZeroizeOnDrop` |
| **Пост-квантовый KEM** | `ML-KEM-768` (NIST FIPS 203) | `ml-kem` (RustCrypto) | Защита от «Harvest Now, Decrypt Later» |
| **Цифровые подписи** | `Ed25519` (RFC 8032) | `ed25519-dalek` | Только `verify_strict` (защита от malleability и малых подгрупп) |
| **AEAD-шифрование пакетов и хранилища** | `ChaCha20-Poly1305` (RFC 8439) и `XChaCha20-Poly1305` | `chacha20poly1305` | 96-битный nonce для рэтчета; 192-битный случайный nonce (`XChaCha20`) для `AccountVault` и файлов |
| **Очистка секретов в ОЗУ** | Зануление памяти при выходе из области видимости | `zeroize` | Обязательный `Zeroize` + `ZeroizeOnDrop` на всех структурах ключей |
| **Слепые подписи (`SupporterPass`)** | Privacy Pass / Blind Signatures | `blind-rsa-signatures` / Ristretto-based blind token в `aegis-crypto` | Несвязываемость платежа доната и слота аккаунта |
| **Шифрование локальной БД** | `SQLCipher 4` (`AES-256-CBC` + `HMAC-SHA512`) | `rusqlite` (`bundled-sqlcipher-vendored-openssl`) | Страница 4096 байт, `PRAGMA cipher_memory_security = ON` |

## 3. Спецификация пост-квантового гибридного обмена ключами (Aegis-PQXDH)

Для защиты переписки от ретроспективной расшифровки квантовым компьютером (**Harvest Now, Decrypt Later**) каждое новое 1:1 соединение в Aegis инициализируется гибридным протоколом **Aegis-PQXDH**, объединяющим `X25519` и `ML-KEM-768` (FIPS 203).

### 3.1 Состав приглашения / связки ключей получателя (`PreKeyBundle`)
Когда Боби (`B`) создаёт одностороннюю очередь или генерирует инвайт (QR / ссылку `aegis://invite/...`), связка ключей содержит:
- $IK_B$: публичный ключ идентичности контакта (`Ed25519` + конвертируемый или парный `X25519`);
- $SPK_B$: подписанный классический пре-ключ (`X25519`), подписанный $IK_B$;
- $PQSPK_B$: подписанный пост-квантовый пре-ключ инкапсуляции **`ML-KEM-768` (`ek`, 1184 байта)**, подписанный $IK_B$;
- $OPK_B$ (опционально при онлайн-обмене): одноразовый классический (`X25519`) и/или одноразовый `ML-KEM-768` ключ.

### 3.2 Вычисление общего мастер-секрета (`SK`)
Алиса (`A`), инициируя сессию с Бобом (`B`):
1. Проверяет строгие подписи `Ed25519` (`verify_strict`) на $SPK_B$ и $PQSPK_B$. При любой ошибке — **Fail Closed**.
2. Генерирует эфемерную пару $EK_A$ (`X25519`) и выполняет классические вычисления Диффи-Хеллмана:
   - $DH_1 = \text{X25519}(IK_A, SPK_B)$
   - $DH_2 = \text{X25519}(EK_A, IK_B)$
   - $DH_3 = \text{X25519}(EK_A, SPK_B)$
   - $DH_4 = \text{X25519}(EK_A, OPK_B)$ (если присутствует $OPK_B$)
3. Выполняет пост-квантовую инкапсуляцию `ML-KEM-768`:
   - $(CT_{KEM}, SS_{KEM}) = \text{ML-KEM-768.Encaps}(PQSPK_B)$, где $|CT_{KEM}| = 1088$ байт, $|SS_{KEM}| = 32$ байта.
4. Объединяет классические и пост-квантовый секреты через криптостойкий гибридный комбайнер:
   $$\text{IKM} = F \parallel DH_1 \parallel DH_2 \parallel DH_3 \parallel [DH_4] \parallel SS_{KEM}$$
   $$\text{TranscriptHash} = \text{BLAKE3}(IK_A \parallel IK_B \parallel EK_A \parallel SPK_B \parallel PQSPK_B \parallel CT_{KEM})$$
   $$SK = \text{HKDF-SHA256}(\text{salt} = \text{TranscriptHash}, \text{ikm} = \text{IKM}, \text{info} = \text{"AEGIS\_PQXDH\_X25519\_MLKEM768\_V1"})$$
5. Инициализирует `Double Ratchet` корневым ключом $SK$. Все промежуточные буферы ($DH_1..DH_4$, $SS_{KEM}$, $\text{IKM}$) немедленно очищаются через `zeroize`.
6. **Гарантия безопасности:** секрет $SK$ остаётся нераскрытым, пока стойким остаётся **хотя бы один** из примитивов (`X25519` ИЛИ `ML-KEM-768`).

## 4. Спецификации защитных подсистем протокола (D-0006..D-0011)

### 4.1 Адаптивный Proof-of-Work (`Anti-DDoS Shield`, D-0007)
- **Формат пазла:** сервер выдаёт структуру `PowChallenge { version: u8, difficulty_bits: u8, timestamp_unix: u64, context_tag: [u8; 16], server_signature: [u8; 64] }`.
- **Верификация решения (`PowSolution`):** клиент ищет `nonce: u64`, для которого первые `difficulty_bits` бит хэша `BLAKE3("aegis.pow.v1" || challenge_bytes || nonce.to_le_bytes())` равны нулю.
- Сервер проверяет свою подпись `server_signature` (не храня состояние выданных пазлов в БД — **Stateless Challenge**), проверяет свежесть `timestamp_unix` (окно 120 секунд), проверяет ведущие нули хэша за $O(1)$ и помечает `challenge_hash` в быстром in-memory Bloom/LRU-фильтре во избежание повторного использования (replay).

### 4.2 Алгоритм локального DLP-анализатора `LeakGuard` без ложных срабатываний (D-0009)
Модуль `aegis_protocol::leak_guard::scan_outgoing_text(text: &str, own_nickname: &str) -> LeakScanResult` работает полностью офлайн внутри Rust-ядра до шифрования:
1. **`FindingKind::PaymentCard` (Банковская карта + CVV):**
   - Из текста выделяются последовательности цифр длиной от 13 до 19 цифр, допускающие разделители только в виде одиночных пробелов или дефисов на стандартных границах групп по 4 цифры.
   - Проверяется префикс платёжной системы (Visa `4`, Mastercard `51–55`, `2221–2720`, Mir `2200–2204`, AmEx `34, 37`, UnionPay `62`).
   - **Обязательный фильтр Луна (Luhn Check):** вычисляется контрольная сумма по модулю 10. Если сумма не кратна 10 — последовательность **немедленно отбрасывается** (0% ложных срабатываний на случайных ID заказов или таймкодах).
   - Если проверка Луна прошла, детектор дополнительно сканирует окрестность ±40 символов на наличие паттерна срока действия `(0[1-9]|1[0-2])\/([0-9]{2}|[0-9]{4})` и 3/4-значного `CVV/CVC`, повышая уровень угрозы до `Severity::Critical`.
2. **`FindingKind::PhoneNumber` и `FindingKind::EmailAddress`:**
   - Email проверяется по структуре `local@domain.tld`, где `tld` сверяется со встроенным отсортированным списком валидных доменных зон верхнего уровня (без сетевых запросов).
   - Телефон срабатывает только при наличии явного международного префикса (`+7`, `+1`, `+44` и др.) или структурного форматирования с кодом оператора и длиной 10–15 цифр (исключая даты вида `2026-10-20` и диапазоны чисел).
3. **`FindingKind::CryptoSeedOrKey` и `FindingKind::OwnNickname`:**
   - Проверка на последовательности из 12 или 24 слов из канонического словаря `BIP-39`, ключи формата `WIF` / `0x[0-9a-fA-F]{64}` и прямое вхождение секретного логина `own_nickname` текущего профиля.

### 4.3 Квота мультиаккаунтов (`MAX_FREE_ACCOUNTS = 3`) и `SupporterPass` (D-0010)
- Локальный менеджер профилей в `aegis-identity` / `aegis-storage` разрешает создание слотов `slot_index` `0`, `1`, `2` (всего **3 изолированных аккаунта**) без токенов.
- При вызове `create_profile` для `slot_index >= 3` ядро требует валидный `SupporterPassToken`:
  - Токен представляет собой пару `(token_nonce: [u8; 32], unblinded_signature: Vec<u8>)`, созданную по протоколу слепой подписи.
  - Ядро проверяет подпись публичным ключом выпуска токенов фонда (`SUPPORTER_ISSUER_PUBKEY`), зашитым в `aegis-directory`, и сохраняет хэш погашенного токена в локальном реестре слотов.

### 4.4 Канал анонимных тикетов в поддержку (D-0006, D-0011)
- Аккаунты и очереди официальной поддержки сопровождаются структурой `SupportRoleCert { support_pubkey: Ed25519PubKey, encryption_kem_key: HybridKemPubKey, valid_until: u64, signatures: Vec<MofNSignature> }`.
- Когда пользователь создаёт обращение в поддержку (из клиента или через совместимый веб-портал), формируется структура `SupportTicketPayload` (категория вопроса, текст, опциональный публичный токен доната, одноразовый ключ обратного канала `reply_queue_write_cap`), которая шифруется гибридным ключом `encryption_kem_key` (`X25519 + ML-KEM-768`) поддержки. Сервер-посредник не может прочитать содержимое тикета.
