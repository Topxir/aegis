## 1. Активы (Assets)

Все данные в системе Aegis классифицируются по критичности и месту хранения. Главный принцип: **секреты существуют в открытом виде только в оперативной памяти клиентского ядра (`zeroize`-буферы) в момент использования**.

| ID | Актив | Критичность | Где хранится | Чем защищён | Последствия компрометации |
|---|---|---|---|---|---|
| **A-01** | **Мастер-пароль и производные ключи (`KEK_password`, OPAQUE `export_key`)** | Критическая | Только в памяти в момент логина/регистрации; не хранится на диске | Строгий стандарт пароля (>=12 симв., >=3 заглавных, строчные, цифры, спецсимволы, скоринг энтропии, D-0006), клиентский `Argon2id`, протокол `OPAQUE` (RFC 9807), `Zeroizing` | Доступ к `AccountVault` на сервере и возможность расшифровать локальную БД при наличии физического доступа к устройству |
| **A-02** | **Ключ локальной БД (`DB_KEY`, 256 бит) и ключи файлов вложений** | Критическая | Локальное хранилище в обёрнутом виде; в RAM только при разблокированном профиле | Двойная обёртка (`KEK_password` + аппаратный ключ `Android Keystore / StrongBox / iOS Secure Enclave` под PIN с аппаратным счётчиком попыток); `SQLCipher` (AES-256-CBC + HMAC-SHA512) | Чтение локальной истории сообщений, контактов и ratchet-состояний на конкретном изъятом устройстве |
| **A-03** | **Долгосрочные ключи идентичности и сессий (`Identity Key`, `Signed PreKey`, гибридные `X25519 + ML-KEM-768` ключи, состояния `Double Ratchet` / `MLS`)** | Критическая | Внутри зашифрованной `SQLCipher` БД и зашифрованного конверта `AccountVault` | `XChaCha20-Poly1305` / `ChaCha20-Poly1305`, прямая секретность (Forward Secrecy) и Post-Compromise Security (PCS) в Double Ratchet / PQXDH | Подмена личности в существующих чатах; при наличии FS/PCS старые сообщения остаются защищёнными после шага рэтчета |
| **A-04** | **Зашифрованный облачный конверт очередей (`AccountVault`)** | Высокая | На сервере внутри OPAQUE-записи и в локальном кэше | Шифрование AEAD (`XChaCha20-Poly1305`) на ключе, выведенном из OPAQUE `export_key` (сервер видит только непрозрачный блоб фиксированного размера) | Без `export_key` атака невозможна; при компрометации `export_key` раскрывается список активных односторонних очередей аккаунта |
| **A-05** | **Содержимое переписки, файлы, голосовые и медиа-потоки звонков** | Критическая | Локальная зашифрованная БД; в сети и очередях сервера — только в зашифрованном виде с TTL | Сквозное шифрование (E2EE: Double Ratchet / MLS для чатов, SRTP + SFrame для звонков), удаление с сервера сразу после доставки | Нарушение конфиденциальности переписки |
| **A-06** | **Секретный ник (логин) пользователя** | Высокая | Только в памяти при вводе и в зашифрованном `AccountVault` | На сервер передаётся только необратимый `login_id = Argon2id/BLAKE3(nickname, server_salt)` в рамках OPAQUE; генератор случайных криптостойких ников при регистрации (D-0006) | При утечке самого ника злоумышленник может узнать `login_id` и пытаться инициировать OPAQUE-сессии (защищено PoW и строгим паролем) |
| **A-07** | **Граф контактов и метаданные общения (кто, с кем, когда, размер)** | Высокая | Только в локальной БД клиента | Односторонние анонимные очереди с попарными ротируемыми ID (`QueueId`), `Sealed Sender` (отправитель скрыт внутри E2EE), фиксированный паддинг пакетов (`256 B`, `1 KB`, `4 KB`, `16 KB`) | Построение социального графа пользователей и корреляция активности |
| **A-08** | **IP-адрес клиента и сетевой маршрут** | Высокая | Временное сетевое соединение в ОЗУ транспорта/сервера (без записи на диск) | **Network Anonymity Shield** (D-0008): поддержка Tor (`Arti`/Onion), SOCKS5/VPN, Kill Switch, отсутствие IP-логов на сервере, режим **Relay-Only (TURN)** для всех звонков | Геолокация и сетевая деанонимизация пользователя провайдером, собеседником или оператором сервера |
| **A-09** | **Чувствительные данные пользователя, вводимые в чат (банковские карты, CVV/CVC, телефоны, email, сид-фразы, личный логин)** | Высокая | Буфер ввода сообщения на клиенте | Локальный офлайн DLP-сканер **`LeakGuard`** (D-0009) с проверкой Луна (Luhn) и контекста перед шифрованием | Само-деанонимизация пользователя или кража финансовых средств при фишинге/социальной инженерии |
| **A-10** | **Слоты мультиаккаунтов (до 3 бесплатно) и анонимные донат-токены (`SupporterPass`)** | Средняя | Локальная БД (`aegis-storage`) | Схема слепой подписи **Privacy Pass / Blind Signatures** (D-0010): токен подписан фондом вслепую и не связывает транзакцию доната с `login_id` или устройством | Попытка связать платёж доната с конкретным профилем мессенджера или обход квоты мультиаккаунтов спамерами |
| **A-11** | **Каталог серверов и сертификаты поддержки с галочкой ✓** | Высокая | Подписанный реестр в `aegis-directory` | Пороговая схема подписей **M-of-N Ed25519** ключами фонда + список отзыва (`CRL`) (D-0011) | Фишинг через поддельный сервер или фальшивый аккаунт «Техподдержки» |

## 2. Границы доверия (Trust Boundaries)

Архитектура Aegis разделена на жёсткие зоны доверия с принципом **Fail Closed** на каждом переходе границы:

```
+-----------------------------------------------------------------------------------+
| УСТРОЙСТВО ПОЛЬЗОВАТЕЛЯ                                                           |
|                                                                                   |
|  +---------------------------+      UniFFI API      +--------------------------+  |
|  | TB-1: Hardware Keystore   | <==================> | TB-2: Крипто-ядро Rust   |  |
|  | StrongBox / SecureEnclave |                      | aegis-crypto / identity  |  |
|  | (PIN-счётчик в железе)    |                      | aegis-storage / protocol |  |
|  +---------------------------+                      | (Zeroize RAM, LeakGuard) |  |
|                                                     +------------+-------------+  |
|                                                                  |                |
|                                       Узкое API без ключей       | E2EE пакеты    |
|                                   +------------------------------+-------------+  |
|                                   v                                            v  |
|  +----------------------------------+             +----------------------------+  |
|  | TB-3: UI-слой (aegis-ui-*)       |             | TB-4: WASM-песочница       |  |
|  | Отрисовка, ввод, запрет скринов  |             | aegis-plugins (wasmtime)   |  |
|  | Не имеет доступа к сырым ключам! |             | Манифест прав, сеть выкл.  |  |
|  +----------------------------------+             +----------------------------+  |
+-----------------------------------------------------------------------------------+
                                            |
              TB-5: Недоверенная сеть (TLS 1.3 / QUIC + Паддинг + Tor / VPN)
                                            v
+-----------------------------------------------------------------------------------+
| TB-6: СЕРВЕР ФЕДЕРАЦИИ (Untrusted Postman — aegis-server)                         |
| Видит только: анонимные очереди с шифротекстом, OPAQUE-записи по login_id, PoW.   |
| НЕ ЗНАЕТ: ников, паролей, ключей, отправителей (Sealed Sender), графа контактов.  |
+-----------------------------------------------------------------------------------+
                                            ^
              TB-7: Офлайн-ключи фонда (M-of-N Ed25519) -> aegis-directory
```

1. **TB-1: Аппаратный модуль безопасности (Hardware Keystore / StrongBox / Secure Enclave / TPM)** — изолированная среда хранения ключа-обёртки для PIN. Аппаратно контролирует лимит попыток ввода PIN и время задержки между попытками.
2. **TB-2: Доверенное клиентское ядро (`aegis-crypto`, `aegis-identity`, `aegis-storage`, `aegis-protocol`, `aegis-transport`)** — скомпилированный Rust-код (`#[forbid(unsafe_code)]` в прикладных крейтах). Единственная зона, где существуют ключи в RAM (в обёртках `Zeroizing<T>`) и открытый текст при шифровании/проверке `LeakGuard`.
3. **TB-3: Платформенный UI (`aegis-ui-android`, `aegis-ui-desktop`, `aegis-ui-ios`)** — взаимодействует с ядром исключительно через типизированный слой FFI/UniFFI (AGENTS.md §2 п.6, §4). UI никогда не получает криптографические ключи или внутренние состояния рэтчета.
4. **TB-4: Песочница плагинов (`aegis-plugins`)** — изолированная среда исполнения `wasmtime`. Плагины не имеют доступа к файловой системе, сети (по умолчанию) и ключам; получают только явно разрешённые манифестом события.
5. **TB-5: Сетевой транспорт (Direct / VPN / Tor)** — полностью недоверенная среда. Весь трафик защищён поверх E2EE ещё и транспортным шифрованием TLS 1.3 / QUIC с пиннингом сертификатов сервера и выравниванием размеров пакетов (паддингом).
6. **TB-6: Сервер федерации (`aegis-server`)** — рассматривается как **недоверенный почтальон (Untrusted Postman)**. Сервер может быть взломан, изъят в дата-центре или изначально поднят атакующим. Безопасность содержимого, паролей и социального графа не зависит от честности сервера.
7. **TB-7: Инфраструктура каталога и фонда (`aegis-directory`)** — офлайн-ключи фонда с пороговой подписью `M-of-N Ed25519`. Даже компрометация GitHub-репозитория или одного ключа при `M > 1` не позволяет подделать галочку ✓ сервера или сертификат поддержки.

## 4. Детальный сценарий 1: «Взломан или скомпрометирован сервер» (Compromised / Malicious Server)

### 4.1 Условия сценария
Атакующий получает полный `root`-доступ к серверу федерации `aegis-server` (или изымает физический диск и дамп оперативной памяти сервера в дата-центре).

### 4.2 Пошаговый анализ: что видит атакующий и почему защита не рушится

1. **Таблица аккаунтов (OPAQUE Records):**
   - **Что лежит в БД сервера:** таблица `accounts(login_id BLOB(32), opaque_record BLOB, vault_ciphertext BLOB, updated_at_bucket INT)`.
   - **Почему нельзя узнать ники:** `login_id` вычисляется клиентом как `BLAKE3_keyed(server_public_salt, Argon2id(nickname))`. Сам ник никогда не передаётся по сети. Случайные сгенерированные ники (например, `silent-vortex-9412`, D-0006) не берутся из публичных профилей соцсетей.
   - **Почему нельзя подобрать пароли (Offline Brute-Force):** `opaque_record` создана по протоколу **OPAQUE (RFC 9807 на Ristretto255)**. Внутри нет хэша пароля в простом виде; для проверки одной гипотезы пароля атакующему необходимо вычислить клиентский `Argon2id` (высокая стоимость по памяти: 64 МБ RAM на попытку) и выполнить операции в группе Ristretto255. При соблюдении строгого стандарта пароля D-0006 (>=12 символов, >=3 заглавных, строчные, цифры, спецсимволы, высокая энтропия) офлайн-перебор математически невыполним.
   - **Почему нельзя прочитать `AccountVault`:** конверт `vault_ciphertext` зашифрован алгоритмом `XChaCha20-Poly1305` на ключе, производимом из `export_key` протокола OPAQUE, который никогда не покидает клиентское устройство и не известен серверу даже в момент успешного входа пользователя.

2. **Таблица односторонних очередей (`queues` и `messages`):**
   - **Что лежит в БД сервера:** обезличенные записи `queues(queue_id BLOB(32), write_cap_pubkey BLOB(32), read_auth_pubkey BLOB(32), ttl_sec INT)` и пакеты `messages(msg_id, queue_id, padded_envelope BLOB, expires_at)`.
   - **Почему сервер не знает, кому принадлежит очередь:** при создании очереди или чтении из неё клиент аутентифицируется одноразовой подписью ключа чтения очереди `read_auth_pubkey`, **не передавая свой `login_id`**. Связь между `login_id` и списком `queue_id` хранится исключительно внутри зашифрованного `AccountVault`.
   - **Почему сервер не знает отправителя (`Sealed Sender`):** отправка сообщения в очередь `queue_id` авторизуется только знанием токена записи `write_cap_token` для этой конкретной односторонней очереди. Сертификат и ключ отправителя зашифрованы внутри E2EE-конверта (`padded_envelope`), а размер пакета выровнен паддингом до фиксированной корзины (`256 B`, `1 KB`, `4 KB` или `16 KB`).
   - **Почему нельзя построить граф контактов:** у каждой пары собеседников для каждого направления создаётся отдельная односторонняя очередь со случайным 256-битным `queue_id`. В БД сервера нет ни одного внешнего ключа, связывающего очередь `A -> B` с очередью `B -> A` или с каким-либо аккаунтом.

3. **Оперативная память сервера (RAM):**
   - В ОЗУ сервера находятся только эфемерные TLS/QUIC-сессии, счётчики скользящих окон Anti-DDoS (по обезличенному хэшу с солью, ротируемой каждые 10 минут) и буферы зашифрованных пакетов. Никаких IP-логов на диске или открытых ключей переписки в памяти сервера никогда не существует.

## 5. Детальный сценарий 2: «Изъят или украден телефон / компьютер» (Seized Device)

### 5.1 Состояние А: «Холодное устройство» (выключено или перезагружено, Before First Unlock)
1. Вся база данных сообщений, контактов и ключей сессий на диске зашифрована через **SQLCipher (AES-256-CBC + HMAC-SHA512, страница 4096 байт)** случайным 256-битным ключом `DB_KEY`. Вложения на диске зашифрованы индивидуальными ключами `FileKey` (`XChaCha20-Poly1305`).
2. Сам `DB_KEY` не хранится на диске в открытом виде. На диске лежат два зашифрованных слота:
   - **Слот 1 (Повседневный вход по PIN):** `DB_KEY` зашифрован ключом, комбинирующим `Argon2id(PIN, salt)` и аппаратный неэкспортируемый ключ внутри **Android StrongBox / Keystore** (или **iOS Secure Enclave** / системного TPM/Keychain на Desktop).
   - **Слот 2 (Восстановление локального доступа по паролю):** `DB_KEY` зашифрован ключом `KEK_password = Argon2id(master_password, local_salt)`.
3. **При попытке подбора PIN криминалистическим оборудованием:** аппаратный чип безопасности (`StrongBox` / `Secure Enclave`) принудительно увеличивает задержку между попытками и после **N неверных попыток** (по умолчанию `N = 10`, настраивается от 3 до 15) **безвозвратно уничтожает аппаратный ключ слота 1**. После этого вход по PIN становится невозможным физически — требуется полный мастер-пароль аккаунта.

### 5.2 Состояние Б: «Горячее устройство» (разблокировано или заблокировано недавно, After First Unlock)
1. **Мгновенная очистка памяти (`zeroize`):** при сворачивании приложения, выключении экрана или истечении таймера автоблокировки (по умолчанию 1 минута, можно 0 секунд) клиентское ядро вызывает `Zeroizing::drop()` для `DB_KEY` и всех сессионных ключей в RAM и закрывает дескриптор SQLCipher.
2. **Защита экрана и ОС:**
   - Принудительно включён `FLAG_SECURE` на Android и аналогичные флаги ОС: запрет скриншотов, записи экрана и скрытие превью приложения в меню недавних задач.
   - Приложение запрашивает у экранной клавиатуры режим инкогнито (`IME_FLAG_NO_PERSONALIZED_LEARNING`), чтобы слова не сохранялись в пользовательский словарь ОС.
   - Полный запрет системных облачных бэкапов (`allowBackup="false"`, исключение из iCloud Backup): ключи и БД никогда не выгружаются в Google Drive / iCloud.
   - Уведомления по умолчанию не содержат имени отправителя и текста («Новое зашифрованное сообщение»).

### 5.3 Защита при принуждении: Duress-PIN (Принудительный PIN)
1. Пользователь может заранее задать **Duress-PIN** (отличающийся от основного PIN).
2. При вводе Duress-PIN под давлением внешне приложение открывается совершенно штатно за то же самое время (без индикаторов тревоги или пауз), но в зависимости от выбранной пользователем политики выполняет одно из двух действий:
   - **Режим «Тихое крипто-стирание + Чистый профиль» (по умолчанию):** мгновенно перезаписывает нулями и удаляет ключи боевых профилей (`DB_KEY` слотов 1 и 2), монтируя заранее подготовленную БД-обманку (пустую или с безобидными заметками).
   - **Режим «Изолированный ложный профиль»:** открывает только выделенный ложный аккаунт, в то время как основные слоты мультиаккаунтов скрыты и неотличимы от свободных неинициализированных слотов фиксированного размера на диске.

## 6. Дополнительные сценарии атак и эшелонированная защита

### 6.1 DDoS, спам и брутфорс аккаунтов/очередей (`Anti-DDoS Shield`, D-0007)
- **Угроза:** злоумышленник пытается парализовать сервер миллионами новых очередей, зафлудить инвайт-ссылку пользователя или перебрать пароль по сети.
- **Защита:**
  1. **Адаптивный Proof-of-Work (`BLAKE3 PoW`):** перед выполнением ресурсоёмких операций (регистрация, шаг 1 OPAQUE-логина, создание очереди, первый отклик по публичному инвайту) сервер выдаёт подписанный `Challenge(timestamp, random_nonce, difficulty_bits)`. Клиент обязан найти `solution`, при котором `BLAKE3(Challenge || solution)` имеет не менее `difficulty_bits` ведущих нулевых бит. При обычной нагрузке сложность составляет 16–18 бит (~20–80 мс на телефоне), при всплеске атак сервер автоматически поднимает сложность до 22–26 бит.
  2. **Защита от перечисления (Anti-Enumeration):** при запросе OPAQUE-входа для несуществующего `login_id` сервер вычисляет детерминированную псевдослучайную маскирующую запись от секретного ключа сервера и возвращает ответ **идентичного размера и за то же время**, что и для реального аккаунта.
  3. **Изоляция очередей по контактам:** так как каждый контакт пишет в свою выделенную одностороннюю очередь (`QueueId`), при утечке инвайта или спам-атаке пользователь в 1 клик удаляет или ротирует конкретную очередь, не затрагивая остальные чаты и свой аккаунт.

### 6.2 Сетевая деанонимизация и утечка IP/DNS/WebRTC (`Network Anonymity Shield`, D-0008)
- **Угроза:** пользователь думает, что его VPN или Tor работает, но из-за обрыва туннеля или P2P-соединения WebRTC во время звонка раскрывает свой домашний IP-адрес серверу или собеседнику.
- **Защита:**
  1. **Индикатор маршрута в реальном времени:** в шапке приложения всегда отображается статус соединения:
     - 🔒 **Tor / Onion** — соединение идёт через встроенный клиент Tor (`Arti`) или к `.onion`-серверу (максимальная анонимность);
     - 🛡 **VPN / Прокси** — активен системный VPN или настроенный SOCKS5-прокси;
     - ⚠ **Прямой IP** — прямое соединение без прокси/VPN (пользователь явно предупреждён, что сервер видит его IP).
  2. **Сверка IP без сторонних сервисов:** для проверки работы VPN/прокси клиент **никогда не обращается к внешним сервисам** (никаких `cloudflare`, `ipify`, `google`). Вместо этого клиент внутри зашифрованного канала запрашивает у своего целевого сервера Aegis эхо-пакет `NetworkEchoResponse` (видимый сервером хэш/префикс подсети сокетного соединения, не сохраняемый на сервере) и сопоставляет его с локальными сетевыми интерфейсами и статусом туннеля.
  3. **Kill Switch и запрет DNS/WebRTC утечек:** все DNS-запросы при включённом прокси/Tor разрешаются строго внутри туннеля. В модуле звонков (`aegis-calls`) по умолчанию принудительно включён режим **`IceTransportPolicy::Relay` (TURN Relay-Only)**: прямые P2P-кандидаты (`host`, `srflx`, `prflx`) отброшены на уровне ядра, поэтому собеседник никогда не узнает IP-адрес второго участника звонка.

### 6.3 Социальная инженерия и само-деанонимизация в чате (`LeakGuard`, D-0009)
- **Угроза:** в ходе переписки пользователь случайно вставляет из буфера обмена или набирает номер своей банковской карты с CVV, личный телефон, e-mail, крипто-сид или свой секретный логин, тем самым деанонимизируя себя или теряя деньги.
- **Защита (`LeakGuard` — 100% локальный офлайн-анализатор в `aegis-protocol` с нулевым уровнем ложных срабатываний):**
  1. **Банковские карты и CVV/CVC:** детектор извлекает последовательности из 13–19 цифр (игнорируя пробелы и дефисы), проверяет соответствие известным префиксам платёжных систем (BIN) и **обязательно вычисляет контрольную сумму по алгоритму Луна (Luhn algorithm)**. Дополнительно анализируется окно контекста (±40 символов) на наличие срока действия карты (`MM/YY`, `MM/YYYY`) и 3/4-значного `CVV/CVC`. Благодаря обязательной проверке Луна и контекста обычные большие числа, артикулы, таймкоды или ID не вызывают ложных тревог.
  2. **Телефоны и Email:** строгий синтаксический разбор email (с проверкой по встроенному списку существующих TLD IANA) и номеров телефонов (код страны E.164 + длина национальной части, с исключением дат и математических выражений).
  3. **Секреты, крипто-ключи и собственный логин:** проверка текста на вхождение 12/24 слов из словаря BIP-39, приватных ключей (`0x` 64-hex, Bitcoin WIF, PEM-заголовки), а также точного или нечёткого совпадения с секретным ником (`nickname`) активного аккаунта пользователя.
  4. **Реакция клиента:** если `LeakGuard` обнаруживает совпадение, сообщение **не шифруется и не покидает устройство** до решения пользователя. UI подсвечивает опасный фрагмент и предлагает кнопки: **«Скрыть (`****`)»**, **«Редактировать»** или **«Подтвердить отправку»**.

### 6.4 Злоупотребление мультиаккаунтами и деанонимизация через донаты (`SupporterPass`, D-0010)
- **Угроза:** с одной стороны, спамеры могут создавать десятки аккаунтов в одном приложении; с другой стороны, если пользователь решил поддержать проект донатом и открыть 4-й и последующие изолированные профили на устройстве, обычный платёжный чек мог бы связать его личность/кошелёк с аккаунтом в мессенджере.
- **Защита:**
  1. В `aegis-identity` и `aegis-storage` жёстко зафиксирован базовый лимит: **`MAX_FREE_ACCOUNTS = 3` изолированных профиля на устройство бесплатно**.
  2. Для активации 4-го и более профилей используется протокол **слепой подписи (Blind Signatures / Privacy Pass, RFC 9578)**:
     - Клиент генерирует случайный секретный токен `t`, ослепляет его фактором `r` (`blinded_token = Blind(t, r)`) и прикладывает к подтверждению доната.
     - Сервер выдачи токенов подписывает `blinded_token` своим приватным ключом, не видя `t`.
     - Клиент снимает ослепление (`sig = Unblind(blind_sig, r)`) и получает валидный токен `SupporterPass = (t, sig)`.
     - При проверке токена в клиенте или при погашении слота на сервере математически невозможно связать предъявленный `(t, sig)` с транзакцией доната или временем его выпуска.

### 6.5 Подмена сервера, каталога или аккаунта поддержки (D-0006, D-0011)
- **Угроза:** злоумышленник поднимает фишинговый сервер и рисует ему статус «Официальный ✓✓» или пишет пользователю от имени «Поддержки Aegis ✓» с просьбой назвать пароль.
- **Защита:**
  1. Статусы серверов (**Официальный ✓✓**, **Проверенный ✓**) и бейджи **Поддержки ✓** не являются текстовыми полями профиля — это криптографические сертификаты (`ServerCert`, `SupportRoleCert`), подписанные пороговой схемой **M-of-N Ed25519** корневыми ключами фонда, зашитыми в бинарник `aegis-directory`.
  2. Любая ошибка проверки подписи, истечение срока действия сертификата или попадание ключа в подписанный список отзыва (`RevocationList`) приводит к немедленному отказу (**Fail Closed**).
  3. Обращения в поддержку отправляются через встроенную в `aegis-protocol` систему **анонимных зашифрованных тикетов (`SupportTicketPayload`)**, зашифрованных напрямую на проверенный публичный ключ поддержки (совместимую как с клиентским чатом поддержки, так и с будущим официальным веб-порталом тикетов). При этом клиент в интерфейсе тикета дополнительно предупреждает: *«Поддержка никогда не запрашивает ваш пароль или сид-фразу»*.

## 7. Что вне модели угроз (Out of Scope) и честные ограничения

Следующие угрозы явно вынесены за рамки гарантий ядра в текущей версии (PLAN.md §2, §3):

1. **Полная компрометация операционной системы устройства (Root/Jailbreak малварь, аппаратные закладки, Pegasus-класс эксплойтов ядра ОС):** если вредоносный код работает с правами ядра ОС в момент, когда пользователь разблокировал приложение и читает чат, малварь может считывать буфер видеокарты или перехватывать нажатия клавиш до их попадания в `aegis-ui-*`.
2. **Глобальный пассивный противник, контролирующий одновременно все узлы сети и все входные/выходные узлы Tor:** при малом числе активных пользователей (малом множестве анонимности) такой противник может проводить статистическую атаку пересечения (intersection attack) по времени активности пользователей, если не включён постоянный фоновый трафик (cover traffic, запланированный как расширение).
3. **Утечка факта пуш-уведомления на iOS через APNs:** из-за ограничений платформы Apple фоновое пробуждение на iOS требует отправки пустого push-сигнала через серверы APNs. Apple не видит ни текста, ни отправителя, ни ключей, но видит факт пробуждения конкретного устройства. Пользователь iOS явно предупреждается об этом в интерфейсе.
4. **Аппаратные акустические/оптические атаки («взгляд через плечо», скрытая камера над экраном, направленный микрофон во время разговора):** защищаются только организационными мерами самого пользователя.
5. **Утеря мастер-пароля пользователем при отключённой опциональной фразе восстановления (24 слова):** так как ни сервер, ни разработчики не имеют доступа к паролям и ключам (`Zero-Knowledge`), восстановить доступ к зашифрованному `AccountVault` без пароля невозможно по определению.
