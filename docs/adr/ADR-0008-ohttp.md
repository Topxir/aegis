# ADR-0008 — OHTTP RFC 9458 для API

- Статус: **ПРИНЯТО**
- Дата: 2026-10-30
- Компоненты: `aegis-core::transport`, `aegis-relay`, `aegis-account`,
  `aegis-blob`, `aegis-directory`
- Связанные решения: `D-0024`, `D-0025`, `D-0026`

## Контекст

Tor скрывает IP от relay, но relay всё равно видит содержимое запроса
(например, `inbox_id`, `account_id`, путь). OHTTP разделяет роли: gateway
видит IP, но не содержимое; relay видит содержимое, но не IP. Это снижает
корреляцию и защищает от оператора relay, который логирует запросы.

## Решение

Использовать `ohttp`:

- crate: `ohttp`;
- версия: `0.8.0`;
- лицензия: MIT OR Apache-2.0;
- MSRV: 1.86;
- репозиторий: `https://github.com/martinthomson/ohttp`;
- RFC 9458 (Oblivious HTTP), HPKE (RFC 9180);
- gateway — отдельный сервис/оператор от relay;
- клиент инкапсулирует HTTP-запрос; gateway расшифровывает только
  внешний слой и пересылает relay;
- relay не читает `peer_addr()`; gateway не логирует тело;
- ключи gateway публикуются в подписанном directory descriptor; клиент
  проверяет подпись и пиннит ключ;
- ротация ключей — с overlap-периодом; старые ключи отзываются;
- запросы паддируются; размеры — по buckets.

## Почему OHTTP

- Стандарт RFC 9458, решает проблему «IP vs содержимое».
- `ohttp` — Rust-реализация, совместимая с RFC.
- MIT/Apache-2.0 совместимы с AGPL-3.0-or-later.
- Хорошо сочетается с Tor: Tor скрывает IP от gateway, OHTTP скрывает
  содержимое от relay.

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| Только Tor | Relay видит `inbox_id`/`account_id` и путь |
| Только OHTTP | Gateway видит IP; без Tor слабее |
| Свой oblivious proxy | Запрещено; нет аудита |
| Прямой HTTPS | Relay видит IP и содержимое |

## Лицензия и AGPL

MIT OR Apache-2.0. Совместимо с AGPL-3.0-or-later. `ohttp` может тянуть
`bhttp`/HPKE-зависимости; для каждой прямой зависимости — отдельный ADR,
если она попадает в публичный API.

## Аудит и происхождение

- Публичный аудит конкретной версии `0.8.0` не подтверждён.
- RFC 9458/HPKE стандартизированы; это не заменяет аудит кода.
- Внешний аудит gateway/relay разделения и key management — до 1.0.
- При пине проверить OSV/RustSec и GitHub advisories.

## Известные CVE

На 2026-10-30 OSV не возвращает известных уязвимостей для `ohttp 0.8.0`.
Проверять при каждом обновлении, а также для HPKE-зависимостей.

## Риски и ограничения

| Риск | Смягчение |
|---|---|
| Gateway коррелирует с relay | Разные операторы/серверы; OHTTP; минимум логов |
| Компрометация ключа gateway | Ротация; overlap; отзыв; pinning |
| Replay | Одноразовые токены; TTL; nonce |
| Размер запроса | Паддинг; buckets |
| Нет аудита версии | Внешний аудит до 1.0 |

## План проверки

1. RFC 9458 test vectors / тесты `ohttp`.
2. E2E: клиент → gateway → relay; gateway не видит тело, relay не видит IP.
3. Ротация ключей и отзыв.
4. Неверный/просроченный ключ → отказ.
5. Проверить, что gateway/relay не логируют запросы.
6. Нагрузочный тест и паддинг.

## Открытые вопросы

1. Кто оператор gateway? См. Q-25/архитектуру; минимум — отдельный сервер.
2. Нужен ли `bhttp` как прямая зависимость? Если да — ADR.
