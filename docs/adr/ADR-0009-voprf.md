# ADR-0009 — VOPRF RFC 9497 для blind tokens

- Статус: **ПРИНЯТО**
- Дата: 2026-10-30
- Компоненты: `aegis-relay`, `aegis-blob`, `aegis-core::transport`
- Связанные решения: `D-0024`, `D-0026`

## Контекст

Relay и blob store должны выдавать квоты/токены, не связывая их с
аккаунтом или IP. Нужны blind tokens для отправки/скачивания и защита от
spam. PoW один недостаточен; нужен анонимный токен.

## Решение

Использовать `voprf`:

- crate: `voprf`;
- версия: `0.5.0` (stable; `0.6.0-pre.*` не использовать в проде);
- лицензия: MIT;
- MSRV: 1.65;
- репозиторий: `https://github.com/facebook/voprf`;
- RFC 9497 (VOPRF);
- blind token выдаётся отдельно от использования: клиент получает токен
  через OHTTP/Tor, relay проверяет его при отправке;
- `token_id` — 16-байтный handle; полный токен передаётся в отдельном
  поле/заголовке и не логируется;
- токены одноразовые; TTL; защита от double-spend в RAM;
- PoW минимум 16 бит как дополнительный барьер;
- issuer и relay могут быть разными ролями; ключи issuer — в descriptor.

### Ciphersuite

Использовать ciphersuite RFC 9497, поддерживаемый `voprf`. Кандидат —
`ristretto255-SHA512`; окончательный выбор — Phase 2 spike. Смена suite —
через обновление ADR и миграцию токенов.

## Почему VOPRF

- Стандарт RFC 9497, blind tokens без привязки к пользователю.
- Rust-реализация, MIT.
- Позволяет не писать свою blind signature.
- Хорошо сочетается с Privacy Pass-подобной моделью.

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| Своя blind signature | Запрещено |
| Blind RSA | Другой размер/производительность; меньше подходит для мобильных |
| Только PoW | Не даёт анонимной квоты; спам возможен |
| Аккаунтные квоты | Связывают токен с `account_id` |

## Лицензия и AGPL

MIT. Совместимо с AGPL-3.0-or-later.

## Аудит и происхождение

- Публичный аудит конкретной версии `0.5.0` не подтверждён.
- RFC 9497 и академический анализ VOPRF; это не заменяет аудит кода.
- Внешний аудит issuance/verification и double-spend — до 1.0.
- При пине проверить OSV/RustSec.

## Известные CVE

На 2026-10-30 OSV не возвращает известных уязвимостей для `voprf 0.5.0`.
Проверять при каждом обновлении.

## Риски и ограничения

| Риск | Смягчение |
|---|---|
| Double-spend | Одноразовые токены; RAM-реестр; TTL |
| Issuer связывает выдачу и использование | Разделение ролей; OHTTP/Tor; минимум метаданных |
| Слабый токен/ключ | Пин; аудит; ротация |
| Потеря токенов при рестарте | RAM-only by design; клиент получает новые |
| Нет аудита версии | Внешний аудит до 1.0 |

## План проверки

1. RFC 9497 test vectors.
2. Issue → use → double-spend reject.
3. Просроченный/поддельный токен → отказ.
4. Проверить, что токен не связан с `account_id`/IP.
5. Нагрузочный тест и rate limit.
6. Фаззинг парсеров токенов.

## Открытые вопросы

1. Кто issuer: relay, отдельный сервис или directory? Предварительно
   отдельный issuer, чтобы не связывать с relay.
2. Нужны ли Privacy Pass extensions? Пока нет; только RFC 9497.
