# ADR-0005 — opaque-ke для OPAQUE RFC 9807

- Статус: **ПРИНЯТО**
- Дата: 2026-10-30
- Компонент: `aegis-account`, `aegis-core::account`
- Связанные решения: `D-0024`, `D-0025`, `D-0026`

## Контекст

OPAQUE — opt-in account service для восстановления seed и списка устройств.
Seed-only остаётся режимом по умолчанию. Сервер не должен хранить пароль,
сообщения или контакты. Прототип использовал HMAC-схему под названием
«OPAQUE», которая не соответствует RFC 9807 (`B-0094`).

## Решение

Использовать `opaque-ke`:

- crate: `opaque-ke`;
- версия: `4.0.1` (stable; `4.1.0-pre.*` не использовать в проде);
- лицензия: Apache-2.0 OR MIT;
- MSRV: 1.85;
- репозиторий: `https://github.com/facebook/opaque-ke`;
- RFC 9807;
- KSF — Argon2id через `argon2` (ADR-0006);
- сервер хранит только OPAQUE registration record (verifier/envelope),
  зашифрованный seed-backup и подписанный device list;
- пароль и seed-backup plaintext никогда не логируются и не попадают в
  БД в открытом виде;
- одинаковые ошибки login/registration, rate limit, PoW.

### Ciphersuite

Использовать ciphersuite из RFC 9807, поддерживаемый `opaque-ke` и
совместимый с Argon2id KSF. Конкретный suite фиксируется в Phase 2 spike и
тестах; менять его без миграции нельзя.

## Почему opaque-ke

- Реализация RFC 9807 на Rust.
- Есть публичный аудит NCC Group (2021) для ранней версии; исправления
  вошли в `v1.2.0`. Это полезный сигнал, но **не** аудит `4.0.1`.
- Apache-2.0/MIT совместимы с AGPL-3.0-or-later.
- Позволяет не писать свой OPRF/AKE.

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| Своя «OPAQUE» на HMAC | Не RFC 9807; запрещено; уже привело к `B-0094` |
| Пароль + Argon2id на сервере | Сервер видит пароль/хэш; offline guessing |
| SRP | Другой протокол; меньше современной поддержки |
| OPAQUE на P-256 | Возможно, но suite нужно согласовать с клиентом/сервером; Ristretto255 предпочтителен |

## Лицензия и AGPL

Apache-2.0 OR MIT. Совместимо с AGPL-3.0-or-later. Сохранить уведомления.

## Аудит и происхождение

- NCC Group audit (June 2021) — `opaque-ke v0.5.0`; fixes в `v1.2.0`.
  Отчёт публичный.
- `4.0.1` не покрыт этим отчётом; нужен внешний аудит текущей версии до
  1.0.
- При пине проверить OSV/RustSec и GitHub advisories.

## Известные CVE

На 2026-10-30 OSV не возвращает известных уязвимостей для
`opaque-ke 4.0.1`. Проверять при каждом обновлении.

## Риски и ограничения

| Риск | Смягчение |
|---|---|
| Offline guessing слабого пароля | Argon2id, сильный пароль, rate limit, предупреждение |
| `account_id` и login timing | Отдельный оператор, OHTTP/Tor, минимум метаданных |
| Компрометация account service | Сервер не видит seed/сообщения; только encrypted backup |
| Ошибка в KSF параметрах | Версионирование параметров; benchmark; ADR-0006 |
| Нет аудита 4.0.1 | Внешний аудит до 1.0 |

## План проверки

1. RFC 9807 test vectors.
2. Registration/login; неверный пароль; повтор; параллельные сессии.
3. Проверить, что сервер не хранит пароль/plaintext seed.
4. Проверить, что login timing/ошибки не раскрывают существование аккаунта.
5. Фаззинг парсеров registration/login сообщений.
6. Тест восстановления seed на новом устройстве.

## Открытые вопросы

1. Какой ciphersuite выбрать? Решение в Phase 2 spike.
2. Нужен ли отдельный OPRF-ключ на аккаунт или общий? Предварительно
   общий с ротацией; фиксируется в PROTOCOL_V2.
