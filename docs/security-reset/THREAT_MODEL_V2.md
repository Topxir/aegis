# Aegis — модель угроз v2 (APPROVED rev.2)

**Статус: УТВЕРЖДЕНО владельцем 2026-10-30. Не является обещанием безопасности.**
Ревизия 2 учитывает ответы владельца: libsignal XEd25519, opt-in OPAQUE,
public alpha после внутреннего red team, P2P после MVP, группы ≤ 20,
только явный экспорт.

Этот документ заменяет оптимистичную модель из `docs/PLAN.md §3`. Он написан
под цель «максимальная практическая анонимность и защита от государственного
уровня», но без ложных гарантий.

## 1. Что мы защищаем

| Актив | Почему важен |
|---|---|
| Содержимое сообщений | Переписка, файлы, группы |
| Идентичность и ключи | Кто с кем говорит, ключи устройства, seed |
| Метаданные | Кто, когда, откуда, как часто, размеры, IP, timing |
| Контактный граф | Список контактов и групп — часто ценнее содержимого |
| Локальные данные | База, вложения, заметки, черновики, ключи |
| Seed-backup и device list | Восстановление аккаунта; список устройств |
| Доступность | Возможность отправить/получить сообщение при блокировках |
| Целостность | Подмена сообщения, ключа, обновления, сервера |
| Код и сборки | Бэкдор в клиенте/сервере/обновлении |

## 3. Цели безопасности

1. **Конфиденциальность** содержимого: только отправитель и получатель.
2. **Целостность и аутентичность**: подмена сообщения/файла/ключа отвергается.
3. **Forward secrecy**: компрометация долгосрочного ключа не раскрывает
   прошлые сообщения.
4. **Post-compromise security**: после компрометации сессия восстанавливается.
5. **Анонимность и unlinkability**: relay не знает, кто с кем и с какого IP;
   сообщения одного пользователя нельзя связать между собой.
6. **Минимизация метаданных**: сервер не хранит контактный граф, IP-логи,
   историю, аналитику. Account service хранит только OPAQUE verifier,
   зашифрованный seed-backup и подписанный device list.
7. **Устойчивость к цензуре**: Tor/OHTTP, несколько relay, P2P позже, зеркала.
8. **Устойчивость к удалению кода/сети**: AGPL, форки, федерация, P2P позже.
9. **Abuse resistance**: PoW, токены, block/report, без серверного чтения
   контента.
10. **Проверяемость**: открытый код, reproducible builds, аудит, SBOM.
11. **Восстановление без глобального идентификатора**: seed-фраза; opt-in
    OPAQUE-аккаунт по `account_id`, производному от seed, без
    ника/телефона/email.

## 4. Не-цели и честные ограничения

Мы **не** обещаем:

- защиту от заражённого устройства, root/jailbreak, malware, keylogger;
- защиту от принуждения пользователя (rubber-hose cryptanalysis);
- защиту от глобального пассивного наблюдателя с неограниченными ресурсами;
- анонимность от человека, с которым пользователь сам делится контактом;
- невозможность удалить сообщение с устройства получателя;
- модерацию контента без нарушения E2EE;
- «100% анонимность» при выключенном Tor и прямом IP;
- безопасность при использовании самописной криптографии;
- безопасность без внешнего аудита и bug bounty;
- криптографическую one-time гарантию инвайта: инвайт — контактная
  карточка, а не одноразовый ресурс;
- автоматический cloud backup: только явный зашифрованный экспорт;
- message franking в MVP: схема ещё не выбрана, свою не пишем;
- защиту от корреляции между account service и relay, если их ведёт один
  оператор;
- защиту от offline guessing слабого OPAQUE-пароля при компрометации
  account service;
- защиту от злоумышленника, который одновременно получил пароль и
  seed-backup: он получает полный контроль над аккаунтом, а device list не
  является криптографическим барьером.

## 5. Допущения

- OS sandbox и keystore (Android Keystore/StrongBox, iOS Secure Enclave,
  desktop keyring) работают корректно.
- Устройство не скомпрометировано malware с правами root.
- Используются audited crypto libraries; мы не пишем примитивы сами.
- libsignal PQXDH/Double Ratchet и OpenMLS обеспечивают заявленные
  свойства; мы не модифицируем их протокол.
- Tor/Arti и OHTTP обеспечивают заявленные свойства; глобальный наблюдатель
  может коррелировать трафик, это остаточный риск.
- OHTTP gateway и account service — отдельные роли/операторы; иначе
  корреляция по IP/timing усиливается.
- Пользователь проверяет safety number/QR при первом контакте.
- Пользователь не отправляет секреты в открытый чат; LeakGuard — только
  вспомогательная защита, не гарантия.
- Часы устройства примерно корректны; TTL/expiry не являются защитой от
  подмены времени.
- Если OPAQUE включён, пользователь выбирает сильный пароль; Argon2id
  повышает стоимость offline guessing, но не делает слабый пароль
  безопасным.

## 6. Границы доверия

```
[Клиент A] --Tor--> [Relay 1/2/3] <--Tor-- [Клиент B]
     |                   |
     |                   +-- RAM-only очереди, no logs
     |
     +--OHTTP--> [OHTTP Gateway] (отдельный оператор)
     |
     +--TLS--> [Account service] (OPAQUE + encrypted seed backup)
     |          отдельный оператор; не видит сообщения
     |
     +--P2P onion--> [Клиент B] (после MVP, когда оба онлайн)

[Клиент] --TLS 1.3--> [Blob store] (шифрованные блобы, TTL)
[Клиент] --TLS 1.3--> [Key server] (prekey bundles, OHTTP)
[Платформа] --push--> [Клиент] (только generic wake-up, без контента)
```

Доверяем: audited crypto libraries, OS keystore, Tor/Arti, TLS 1.3, MLS,
SQLCipher. Не доверяем: relay, account service, key server, blob store,
хостинг, сеть, платформе, push, обновлениям, сборкам, себе-как-разработчику
без проверки.

## 8. «Даже создатель не узнает» — что это значит

Дизайн-цель:

- ключи только на клиенте, сервер не хранит приватные ключи;
- relay не видит отправителя (blind envelope) и не пишет IP-логи;
- OHTTP gateway отделён от relay;
- account service видит только `account_id`, OPAQUE-запись, зашифрованный
  seed-backup и device list; не видит сообщения и контакты;
- нет глобального ника, email, телефона, address book upload;
- нет аналитики, телеметрии, crash-репортов;
- код открыт, сборки воспроизводимы, аудит независимый.

Но:

- создатель/оператор relay всё равно видит **inbox ID, размер, timing**;
  при выключенном Tor — ещё и IP;
- создатель/оператор account service видит **account_id, login timing** и
  факт использования восстановления; при одном операторе с relay это
  коррелирует;
- создатель может выпустить вредоносную сборку; защита — reproducible
  builds, несколько независимых сборщиков, binary transparency, аудит;
- если устройство заражено, создатель тут ни при чём — но данные утекут;
- «создатель» и «оператор» — разные роли; нужно разделение инфраструктуры и
  юридического контроля.

Вывод: **сильно снизить доверие к создателю можно, но абсолютной гарантии
нет.** Это надо писать в UI и документации, а не обещать «математически
невозможно».

## 9. «Невозможно удалить» — что это значит

| Объект | Реалистично | Нереалистично |
|---|---|---|
| Код | AGPL, форки, зеркала (GitHub/Codeberg/self-host), reproducible builds | Запретить любые форки/удаления |
| Сеть | Федерация, P2P позже, несколько юрисдикций, onion-сервисы | Запретить блокировки/изъятие |
| Сообщения | TTL на relay, исчезающие сообщения, нет серверной истории | Удалить сообщение у получателя |
| Аккаунт | Seed-фраза; opt-in OPAQUE seed-backup; удаление account service | Восстановить без seed и пароля |

Блокчейн **не** решает проблему: публичный ledger навсегда фиксирует
метаданные и часто деанонимизирует. Не используем.

## 10. Abuse, закон и App Store

- E2EE + анонимность привлекают не только диссидентов, но и абьюзеров.
- Серверное сканирование контента — это бэкдор; не делаем.
- Компромисс: client-side block/report, rate limits, PoW, прозрачная
  политика. Message franking — только после выбора опубликованной схемы и
  ADR; в MVP не обещаем.
- App Store могут отклонить анонимный E2EE-мессенджер без модерации.
  Поэтому Android: прямой APK/F-Droid; iOS — позже, с честным риском.
- Юрисдикция: выбрать страну с сильной защитой приватности; несколько
  операторов в разных юрисдикциях; warrant canary; transparency report.
- Не обещать помощь в незаконной деятельности; документ описывает
  безопасность, а не обход закона.

## 11. Проверка модели

- Формальный анализ протокола (ProVerif/Tamarin) для PQXDH/Double Ratchet
  и blind envelope.
- RFC/NIST test vectors для всех примитивов; OPAQUE RFC 9807, Argon2id
  RFC 9106, OHTTP RFC 9458, VOPRF RFC 9497, MLS RFC 9420.
- Cross-implementation тесты (Rust/Kotlin/Swift).
- Фаззинг всех парсеров (cargo-fuzz).
- Property-based тесты (proptest).
- Внутренний red team до public alpha.
- Внешний аудит до 1.0 (после финансирования).
- Bug bounty после public alpha.
- Reproducible builds + SBOM + cargo vet.

## 12. Открытые вопросы

Решено владельцем 2026-10-30:

- ✅ Identity key: libsignal XEd25519 (Curve25519 + XEdDSA), не отдельная
  пара Ed25519 + X25519.
- ✅ OPAQUE-аккаунт: opt-in; seed-only остаётся режимом по умолчанию.
- ✅ Public alpha: после внутреннего red team, с меткой «unaudited»;
  внешний аудит — до 1.0.
- ✅ P2P: после MVP.
- ✅ Максимум группы в бете: 20.
- ✅ Бэкап: только явный зашифрованный экспорт; автоматического cloud
  backup нет.

4. Кто будет независимым сборщиком/аудитором при соло-разработке?
5. Какая юрисдикция и юридическая форма проекта?
6. Какой бюджет на аудит и когда его искать?
