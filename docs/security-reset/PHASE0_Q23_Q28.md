## Q-23 — когда ищем грант на внешний аудит

### Варианты

1. **Сейчас, параллельно Phase 0.** Готовить concept note, бюджет и
   milestones; подавать в NLnet/OTF/Prototype Fund, не дожидаясь кода.
2. **После MVP.** Меньше неопределённости, но аудит и разработка
   остаются без финансирования дольше.
3. **После внутреннего red team.** Больше доказательств, но public alpha
   уже можно выпускать без внешнего аудита; грант нужен до 1.0.

### Рекомендация

Вариант 1. Грант нужен прежде всего на **внешний аудит** и, возможно, на
частичную оплату времени разработчика; он не должен быть условием старта
Phase 0/1.

Практический порядок:

1. Подготовить 2–3-страничный concept: проблема, threat model, план
   Phase 0–5, бюджет, deliverables, лицензия AGPL-3.0-or-later.
2. Сделать отдельный бюджет на аудит (ориентир из roadmap: $50k–$250k;
   для первой заявки — консервативно $50k–$150k) и bug bounty.
3. Подавать в фонды, которые финансируют open-source privacy/security.
   Проверить актуальные условия, требования к юрлицу и публичности кода.
4. Если фонд требует публичный репозиторий, предложить: публичные
   спецификации/документы + private code review доступ; либо отдельный
   публичный docs-репозиторий. Это требует решения владельца, потому что
   текущее правило — приватный репозиторий до внутреннего red team.
5. Не обещать в заявке «аудит до public alpha»: по rev.2 public alpha —
   после внутреннего red team, внешний аудит — до 1.0.

### Что блокируется

- Без гранта внешний аудит откладывается до финансирования; 1.0
  блокируется, public alpha — нет.
- Без юрформы/фискального спонсора многие фонды не смогут заключить
  договор.

## Q-24 — кто независимый сборщик/аудитор при соло-разработке

### Варианты

1. **Только CI автора.** Дешево, но не независимо; не считается
   reproducible-проверкой.
2. **Два независимых сборщика.** Один — автор/CI, второй — доверенный
   участник сообщества или отдельная организация; сравнение SHA-256
   артефактов.
3. **Внешняя аудиторская фирма.** Аудит криптографии/протокола/клиента/
   сервера; дорого, нужно финансирование.
4. **Комбинация 2 + 3.** Рекомендуется.

### Рекомендация

- Для reproducible builds: два независимых сборщика, как минимум один —
  не автор. Начать с публичной инструкции и GitHub Actions, затем
  recruiting независимого сборщика из privacy/open-source сообщества.
- Для аудита: внешняя фирма с опытом криптографии/мессенджеров; scope —
  libsignal integration, PQXDH/Double Ratchet usage, invite/inbox,
  OPAQUE account, Tor/OHTTP, SQLCipher key management, supply chain.
- Для bug bounty: после public alpha, минимальный бюджет; не заменяет
  аудит.
- Конкретные люди/фирмы **не выбираются сейчас**: это зависит от бюджета
  и гранта. В заявке можно указать категорию и бюджет, а не обещать
  конкретного подрядчика.

### Что блокируется

- 1.0 и снятие метки «unaudited» — без внешнего аудита.
- Public alpha — нет, достаточно внутреннего red team.

## Q-25 — юрисдикция и юридическая форма

### Варианты

1. **Без юрлица, псевдонимный individual.** Минимум бюрократии, но
   нельзя нормально заключать гранты/договоры, нет liability shield,
   налоговые и банковские сложности.
2. **LLC/аналог в privacy-friendly юрисдикции.** Liability shield,
   банковский счёт, договоры; но регистрация, ежегодные расходы,
   возможное раскрытие бенефициара.
3. **Некоммерческая организация/фонд.** Хорошо для грантов и миссии, но
   governance, отчётность и публичность.
4. **Fiscal sponsor.** Первая заявка идёт через уже существующую
   некоммерческую организацию; быстрее и дешевле, чем создавать свою;
   спонсор берёт на себя финансы/комплаенс. Обычно требует публичной
   информации о проекте.

### Рекомендация

Не создавать свою юрформу до первого гранта/договора. Для первой
заявки — **fiscal sponsor** или партнёрская НКО. Параллельно получить
юридическую консультацию по юрисдикции, налогам, liability и
обязательствам оператора account service. Рассмотреть privacy-friendly
юрисдикции, но не выбирать по слухам: нужны актуальные требования к
бенефициарам, отчётности и защите от SLAPP.

Это чувствительное решение; без юридической консультации его нельзя
считать окончательным.

### Что блокируется

- Грантовые договоры, банковский счёт, часть контрактов на серверы.
- Публичная canary/transparency report и работа account service.

## Q-26 — mixnet (Nym/Loopix) как paranoid mode

### Варианты

1. **Mixnet в MVP.** Сильная защита от timing-корреляции, но высокая
   latency, bandwidth, зависимость, сложность Android и аудита.
2. **Tor + OHTTP + cover traffic в MVP; mixnet после MVP.** Разумный
   компромисс для соло-разработчика.
3. **Никогда.** Не отвечает цели «максимальная практическая анонимность»
   для пользователей под сильным наблюдателем.

### Рекомендация

Вариант 2. В MVP — Tor + OHTTP + паддинг + cover traffic + батчинг.
Mixnet — после MVP, как **opt-in paranoid mode**, только если:
- появится спрос и финансирование;
- latency/батарея приемлемы для мобильных;
- выбран опубликованный протокол/библиотека, а не своя схема;
- есть отдельный ADR и аудит.

Не обещать mixnet в MVP и не добавлять Nym/Loopix в зависимости сейчас.

### Что блокируется

- Ничего в MVP. Это post-MVP тема.

## Q-27 — key transparency сейчас или после аудита

### Варианты

1. **Сейчас, в MVP.** Сильнее защищает от malicious key server, но нужен
   отдельный сервис, gossip/аудит, privacy-анализ и бюджет.
2. **После MVP/аудита.** В MVP — safety number + key-change warning;
   key transparency — отдельный проект.
3. **Никогда.** Оставляет пользователей уязвимыми к подмене ключей
   сервером.

### Рекомендация

Вариант 2. В MVP:
- safety number (QR/60 цифр) для 1:1;
- key-change warning;
- подписанные prekey bundles;
- локальная история ключей.

После MVP/аудита — key transparency как отдельный сервис на
опубликованной схеме (например, transparency log/gossip), без своей
криптографии. Это не блокирует MVP, но должно быть в roadmap.

### Что блокируется

- Более сильная защита от malicious key server; не MVP.

## Q-28 — Android push

### Варианты

1. **FCM.** Не использовать по умолчанию: Google видит metadata, зависимость
   от Play Services, риск цензуры/блокировки.
2. **UnifiedPush + self-hosted ntfy через Tor.** Анонимнее, но нужен
   distributor app, возможны battery/doze проблемы.
3. **Свой WebSocket через Tor + foreground service.** Больше контроля, но
   battery и постоянное соединение.
4. **Без push, только foreground.** Максимальная приватность, худший UX.

### Рекомендация

Кандидат по умолчанию — **UnifiedPush + self-hosted ntfy через Tor**,
с foreground WebSocket fallback. FCM не использовать по умолчанию; если
когда-то добавить, только как явный opt-in с предупреждением.

Требования:
- payload без содержимого («new message»), без отправителя;
- topic rotation;
- возможность отключить push;
- не логировать topic/IP;
- проверить battery/doze на реальных Android-устройствах;
- spike в Phase 2, финальное решение — Phase 3.

### Что блокируется

- Фоновая доставка Android в Phase 3. MVP может начаться с foreground
  WebSocket, push добавить позже.
