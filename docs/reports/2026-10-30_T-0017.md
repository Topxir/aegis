## Критические находки

### 1. Вся криптография — самописная

`Cargo.lock` содержит только 11 workspace-крейтов, **ни одной внешней
зависимости**. `aegis-crypto` реализует SHA-256, HMAC-SHA256, HKDF-SHA256,
ChaCha20, Poly1305, AEAD, Double Ratchet и комбинатор PQXDH вручную.

Риск: даже если RFC-векторы проходят, нет внешнего аудита, защиты от
side-channel, контроля постоянного времени и уверенности в отсутствии
implementation bugs. Это прямо нарушает `AGENTS.md §2.1`.

### 2. «OPAQUE» — не OPAQUE

`aegis-identity/src/lib.rs`:
- `OpaqueClientSession::start` использует `HMAC-SHA256` как OPRF;
- `OpaqueAccountEnvelope::derive_export_key` выводит ключ из
  `nickname:password` через HKDF, без Argon2id;
- `client_public_verifier` — HMAC от пароля/логина;
- `login_id = KDF(nickname, server_salt)`, причём соль есть у сервера.

Риск: это не RFC 9807. При компрометации сервера возможен офлайн-перебор
пароля/ника; заявление «сервер не знает ник» неверно.

### 3. Нет TLS

`aegis-transport` использует `TcpStream` и обычный HTTP. `DirectTls` —
только вариант enum, TLS 1.3 и pinning не реализованы.
`aegis-serverd` слушает `http://` и вручную парсит HTTP.

Риск: активный сетевой противник может MITM/инжектить; метаданные
(пути, queue ID, токены) видны в открытом виде; сервер не аутентифицирован.

### 4. Группы — не MLS

`GroupChatSession` хранит общий `epoch_secret` и шифрует им сообщения.
Это не MLS RFC 9420: нет TreeKEM, нормальной доставки ключей новым членам,
post-compromise security и полноценной forward secrecy.

### 5. Нет реального PQXDH

`combine_pqxdh_secrets` только смешивает два 32-байтных секрета. В ядре нет
реализаций X25519, ML-KEM или Ed25519 — только структуры/заглушки. Значит,
пост-квантовый обмен ключами фактически не реализован.

### 6. Нет встроенного Tor

`TorArtiEmbedded` — вариант enum; зависимости `arti-client` нет. По
умолчанию используются прямые статические IP, что раскрывает IP серверу и
провайдеру. Это противоречит цели максимальной анонимности.

### 7. Чужие статические IP как «официальные»

В каталоге зашиты `185.220.101.42`, `91.108.56.110`, `193.163.125.18`.
Их принадлежность не проверена. Использовать чужие IP как «официальные»
нельзя: это риск перенаправления пользователей и юридических претензий.

### 8. Нет iOS

Есть только `apps/aegis-android` и desktop. iOS отсутствует.

### 9. Тесты не заменяют аудит

98 тестов проходят, но они проверяют самописную реализацию самой собой.
Нет внешнего аудита, bug bounty, формального анализа протокола,
cross-implementation тестов и reproducible build verification.

## Что это значит

Текущий Aegis — ценный прототип: UI, документация, Android/Desktop,
сборки, тесты, UX-идеи. Но его криптографическое ядро нельзя считать
безопасным. Добавлять iOS, группы и файлы поверх него — значит увеличивать
поверхность атаки на небезопасном фундаменте.

Правильный следующий шаг — **security reset**: сохранить UI/доки, заменить
ядро на audited crates и публичные спецификации.

## Решения владельца (2026-10-30)

1. Пока только план и спецификация; код не менять.
2. Идентичность: инвайты + ключи, без глобального ника; seed-only по
   умолчанию + opt-in OPAQUE для восстановления.
3. Сеть: встроенный Tor по умолчанию + OHTTP для API.
4. Репозиторий приватный до внутреннего red team; затем public alpha с
   меткой «unaudited»; внешний аудит — до 1.0.
5. Сначала Android + Desktop; iOS позже.
6. MVP: 1:1 текст + файлы; группы в бете.
7. Ресурсы: соло, без бюджета; внешний аудит позже.
8. Identity key: libsignal XEd25519, не отдельные Ed25519 + X25519.
9. OPAQUE-аккаунт: opt-in.
10. Public alpha: после внутреннего red team.
11. P2P: после MVP.
12. Группы: ≤ 20.
13. Бэкап: только явный зашифрованный экспорт; автоматического cloud
    backup нет.
