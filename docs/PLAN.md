# Aegis — мастер-план

Статус: черновик v0.1. Это **план**, а не приложение. Всё помеченное «⚠ решение» ждёт подтверждения владельца.

---

## 1. Принципы

1. Безопасность > удобство > красота > скорость разработки.
2. Анонимность по умолчанию: ни номера, ни почты, ни телеметрии.
3. Сервер не доверенный: взлом сервера не должен раскрывать содержимое и по возможности связи.
4. Только проверенная криптография. Ничего своего.
5. Простота: чем меньше кода и зависимостей, тем меньше багов и дыр.
6. Открытость: код, протокол, сборки, список серверов, реестр плагинов — на GitHub.
7. Сначала малое число пользователей, архитектура не должна ломаться при росте.

---

## 2. Честные ограничения (важно понимать с первого дня)

- **«Самый защищённый в мире» нельзя провозглашать, это нужно заслужить:** внешний аудит, bug bounty, открытая спецификация, время. Цель формулируем как «защита уровня лучших существующих мессенджеров + максимальная анонимность».
- **Мало пользователей = малое «множество анонимности».** Скрыть трафик среди 50 человек сложнее, чем среди миллионов. Компенсируем паддингом, отсутствием глобальных ID, поддержкой Tor/прокси, сильной защитой метаданных.
- **Телефон как сервер ненадёжен** (NAT, смена IP, батарея, фон). Поэтому «запуск сервера из клиента» = мастер для VPS/десктопа/Docker, а на телефоне только тестовый режим.
- **iOS ограничивает фон:** push только через APNs (Apple видит факт уведомления, не содержимое). Это предупреждаем пользователя честно.
- **Ник + пароль слабее, чем случайный ключ.** Компенсируем: OPAQUE, Argon2id, проверка силы пароля, настоятельная рекомендация длинной фразы.
- **Потеря пароля без recovery = потеря аккаунта.** Это осознанная цена анонимности.

## 3. Модель угроз

| Противник | Что может | Наша защита |
|---|---|---|
| Взломщик сервера | Читать БД, трафик на сервере | E2EE, сервер видит только шифротекст и минимум метаданных, очереди с TTL, нет контактных графов |
| Оператор сервера (злой) | Логи, корреляция | Sealed sender, нет номеров/почт, паддинг, возможность ходить через Tor |
| Сетевой наблюдатель (провайдер) | Видеть соединения | TLS/QUIC, обфускация, прокси/Tor/bridges |
| Кража/изъятие телефона | Доступ к данным | Шифрование БД, PIN с аппаратной защитой и лимитом попыток, wipe, duress-PIN |
| Подмена приложения | Бэкдор | Reproducible builds, подписанные релизы, сборка из открытого кода |
| Вредоносный плагин | Утечка данных | WASM-песочница, манифест прав, плагины не видят ключей |
| Поддельная «поддержка» | Фишинг | Галочка ✓ только по подписи фонда, проверяется в клиенте |
| Квантовый противник (будущий) | «Собрать сейчас, расшифровать потом» | Гибридный обмен ключами с пост-квантовым KEM |

Вне модели (пока): полностью глобальный пассивный противник, компрометация самого устройства малварью с root.

## 4. Идентичность и вход

### 4.1 Регистрация
- Пользователь вводит **ник и пароль**. Больше ничего.
- Ник = логин на сервере. Сервер получает не сам ник, а производный идентификатор (`login_id = KDF(ник, соль сервера)`), поэтому сам ник сервер не хранит.
- Отображаемое имя (то, что видят контакты) отдельное, передаётся только E2EE контактам.
- Пароль на сервер **никогда не уходит**: вход через **OPAQUE** (aPAKE). Даже при взломе сервера пароль не утекает в открытом виде, подбор офлайн резко усложнён.
- Ключи аккаунта создаются на устройстве.

### 4.2 Ключи и PIN (цепочка защиты локальных данных)
```
пароль ──Argon2id──► KEK_пароль ┐
                                 ├─► оборачивают ──► DB_KEY (случайный 256 бит) ──► SQLCipher БД
PIN ──► ключ в Android Keystore/StrongBox (iOS Secure Enclave), счётчик попыток в железе ┘
```
- **Повседневный вход — PIN** (быстро). Опционально биометрия поверх PIN.
- N неверных PIN (по умолчанию 10, настраивается) → ключ-обёртка PIN стирается → нужен ник + пароль.
- **Duress-PIN** (опционально): особый PIN открывает пустой/фальшивый профиль или стирает данные.
- **Переустановка/новое устройство:** сначала ник + пароль (OPAQUE-вход), затем новый PIN. Локальные данные старого устройства при этом не восстанавливаются сами по себе, см. §4.4.

### 4.3 Несколько устройств
- v1: одно устройство на аккаунт. Архитектуру закладываем под несколько (отдельный ключ на устройство, подписанный ключом аккаунта, привязка нового устройства по QR).

### 4.4 Восстановление и бэкапы ⚠ решение
- По умолчанию: **забыл пароль = аккаунт потерян**.
- Опция Фазы 6: **recovery-фраза** (24 слова), показывается один раз.
- Опция: **зашифрованный бэкап истории** (файл или блоб на сервере), ключ из пароля/фразы. Выключен по умолчанию.

## 5. Криптография и протокол

Принцип: используем готовое, комбинируем по доказанным схемам.

| Задача | Выбор (⚠ подтвердить на Фазе 0) |
|---|---|
| Язык ядра | **Rust** (безопасность памяти), биндинги через UniFFI в Kotlin/Swift |
| 1:1 сообщения | Double Ratchet + PQXDH-подобный обмен (X25519 + ML-KEM гибрид), на основе проверенной реализации (libsignal или аналог) |
| Группы | MLS (RFC 9420), реализация OpenMLS, либо Sender Keys на старте |
| AEAD | ChaCha20-Poly1305 / AES-256-GCM |
| Подписи | Ed25519 |
| KDF для пароля | Argon2id |
| Логин | OPAQUE (RFC 9807) |
| Локальная БД | SQLCipher |
| Транспорт | TLS 1.3 / QUIC, пиннинг ключей сервера, опционально обфускация |
| Медиа звонков | SRTP + E2EE-слой (SFrame / insertable streams) |

Метаданные:
- **Sealed sender:** сервер не знает отправителя.
- **Паддинг** сообщений до фиксированных размеров.
- **Минимальное хранение:** очередь доставки с TTL (напр. 30 дней), удаление после доставки.
- **Рекомендуемая идея ⚠ решение:** модель **односторонних очередей без глобальных ID** (как в SimpleX): у каждого контакта своя пара анонимных очередей. Это естественно решает «пользователей нельзя найти» и не даёт серверу строить граф контактов. Сравнить с классической моделью «аккаунт на сервере» до начала Фазы 2.

## 6. Сеть: федерация, свой сервер, список серверов

### 6.1 Серверы
- Любой может поднять сервер. Сервер = «тупой почтальон»: хранит шифротекст в очередях, раздаёт TURN, проверяет подписи, **ничего не знает** о содержимом.
- Что сервер видит и хранит: публичные ключи, OPAQUE-записи, зашифрованные очереди с TTL. Не хранит: ники в открытом виде, номера, почты, IP в логах, контактные списки.
- Один сервер = один бинарь (Rust), SQLite/PostgreSQL, минимальная конфигурация, рассчитан на дешёвый VPS.

### 6.2 Запуск сервера из клиента (`aegis-launcher`)
Режимы:
1. **VPS-мастер:** клиент генерирует `docker-compose`/cloud-init скрипт и инструкцию; владелец вставляет в свой VPS. Показывает адрес, отпечаток ключа сервера, ссылку-приглашение.
2. **Десктоп-режим:** кнопка запускает сервер локально (+ подсказки по проброшу порта / туннелю).
3. **Onion-режим:** сервер доступен как скрытый сервис Tor, IP не раскрывается.
4. **Android (только тест/локальная сеть).** Не рекомендуется для постоянной работы.

### 6.3 Список серверов и галочки ✓
- В клиенте встроенный **каталог серверов** (`aegis-directory`): подписанный JSON в репозитории, публичный ключ каталога зашит в приложение.
- Уровни:
  - **Официальный ✓✓** — поднят проектом.
  - **Проверенный ✓** — прошёл чек-лист: сборка из открытого кода (хэш сходится), no-logs заявление, контакт поддержки, аптайм.
  - **Сообщество** — без галочки, с предупреждением. Любой сервер можно добавить вручную по ссылке.
- **Галочка — это подпись, а не флаг на сервере.** Клиент проверяет подпись; сервер не может сам себе «нарисовать» ✓. Есть список отзыва (revocation) на случай компрометации.
- **Галочка у аккаунтов поддержки:** сертификат, привязывающий публичный ключ контакта к роли «Поддержка», подписанный ключом фонда. Клиент проверяет и показывает ✓. Подделать нельзя.

### 6.4 Общение между серверами ⚠ решение
- Вариант A: клиент пишет напрямую в очередь на сервере получателя (лучше для метаданных).
- Вариант B: серверы пересылают друг другу (S2S), сервер отправителя узнаёт сервер получателя.
- Рекомендация: A (в связке с односторонними очередями).

## 7. Невидимость пользователей

- **Нет поиска по нику, нет «людей рядом», нет списка пользователей.**
- Контакты добавляются только по **приглашению**: одноразовая ссылка / QR / код. Приглашение содержит анонимный адрес очереди + ключи, срок жизни настраивается.
- Ник не публичен: его видят только те, кому ты его передал.
- Защита от перебора: одинаковые ответы сервера на «существует/не существует», rate limit, proof-of-work для массовых действий.
- Верификация контакта: **safety number / QR-сравнение** + предупреждение при смене ключа.

## 8. Фон, звонки, задержка

### 8.1 Сообщения в фоне
- **Android:** foreground-сервис с постоянным соединением (адаптивный keep-alive под батарею) + **UnifiedPush** (без Google). FCM как опция, выключена по умолчанию, только «пустой будильник» без содержимого.
- **iOS:** APNs, пустой push + Notification Service Extension, расшифровка на устройстве. Честно предупреждаем о метаданных.
- Уведомления: режим «скрывать текст/имя», «скрывать всё».

### 8.2 Звонки и видео
- WebRTC-стек, сигнализация через защищённый канал сообщений.
- **E2EE медиа** поверх SRTP.
- **TURN в составе сервера**; режим **relay-only** (скрывает IP собеседников друг от друга).
- Opus для голоса, VP9/AV1/H.264 для видео, адаптивный битрейт, подавление шума.
- Цель по задержке: односторонняя < 150 мс в нормальной сети; цели измеряются в CI на эмуляции сети.
- Групповые звонки: позже, через SFU с E2EE.

### 8.3 Низкий пинг
- QUIC/0-RTT где безопасно, один постоянный мультиплексированный канал, компактный бинарный формат, ограничение паддинга до разумного.

## 9. Хранение на устройстве

- SQLCipher БД, ключ `DB_KEY` защищён по §4.2.
- Вложения шифруются отдельно (ключ на файл).
- Безопасное удаление: стирание ключей (crypto-erase), исчезающие сообщения.
- Защита экрана: блок скриншотов, скрытие в списке приложений, режим инкогнито-клавиатуры.
- Никаких данных в облачных бэкапах ОС (отключено).

## 10. Плагины и моды

- **Темы/моды интерфейса:** декларативные (токены цвета, шрифты, иконки, раскладки), без исполняемого кода. Безопасно по определению.
- **Плагины:** WASM в песочнице (wasmtime), **манифест прав** (читать сообщения чата X, отправлять в чат Y, сеть через прокси, и т.д.). Права запрашиваются явно, отзываются в любой момент.
- Плагины **никогда не получают ключи**, доступ к расшифрованным данным только через узкое API по разрешению.
- **Реестр плагинов** на GitHub: PR-модель, подписи, воспроизводимая сборка, статус «проверен». Сеть у плагинов выключена по умолчанию.
- Анонимные авторы допустимы (подпись ключом, а не личностью).
- Возможные виды: боты, темы, стикеры, переводчики, автоответчики, мосты.

## 11. UI/UX (удобство при максимальной безопасности)

- Онбординг за 3 экрана: ник → пароль (с оценкой силы) → PIN → выбор сервера (по умолчанию официальный ✓✓).
- Для сервера — «Поднять свой» одной кнопкой (мастер §6.2).
- Понятные индикаторы: 🔒 шифрование, ✓ проверенный сервер/поддержка, ⚠ смена ключа контакта.
- Настройки «Простые / Продвинутые»: по умолчанию безопасные значения.
- Тёмная/светлая тема, доступность, локализация (RU/EN с самого начала).
- Принцип: опасные действия (экспорт, ослабление защиты) — с явным подтверждением.

## 12. Open source, GitHub, анонимность проекта

- Монорепо или набор репо по модулям; лицензия ⚠ решение (AGPL для сервера и ядра рекомендуется, чтобы форки не закрывали код).
- Анонимность авторов: проектная идентичность, без личных данных в git-метаданных, подпись релизов проектным ключом.
- **Reproducible builds**, публикация хэшей, F-Droid и прямой APK (Google Play опционально).
- CI: сборка, тесты, фаззинг, аудит зависимостей, SBOM.
- `SECURITY.md`, bug bounty, warrant canary, прозрачный changelog.
- Документы-«память» для ИИ-агента: `AGENTS.md`, `docs/STATE.md`, `DECISIONS.md`, `BUGS.md`, `QUESTIONS.md`, `reports/`.

## 14. Что ещё можно добавить (идеи)

**Безопасность и анонимность**
- Duress-PIN (ложный профиль / тихий wipe) и «паник-кнопка»
- Маскировка приложения (иконка/название калькулятора)
- Блокировка отдельных чатов своим PIN
- Поддержка Tor, SOCKS5, bridges и обфускация против цензуры
- Скрытые сервисы (onion) для серверов
- Cover traffic (фоновый шум), когда пользователей мало
- Предупреждения о подозрительной смене ключей, tamper-detection
- Зашифрованные заметки «Избранное» только на устройстве
- Режим «только офлайн-приглашения» (QR при личной встрече)

**Удобство**
- Голосовые, видео-кружки, файлы, стикеры, реакции, ответы, редактирование
- Локальный поиск по переписке (индекс внутри зашифрованной БД)
- Исчезающие сообщения, таймеры на чат
- Мультипрофили (несколько ников в одном приложении)
- Экспорт/импорт зашифрованного бэкапа
- Живая миграция на другой сервер без потери контактов

**Экосистема**
- Боты и мосты (Matrix/XMPP) как плагины
- Магазин тем и звуковых пакетов
- Документация для операторов серверов, панель мониторинга без личных данных
- Публичный дашборд аптайма серверов из каталога
